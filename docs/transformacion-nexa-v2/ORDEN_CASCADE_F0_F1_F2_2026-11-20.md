## CAMBIO DE DIRECCIÓN: UNA SOLA VERSIÓN DEFINITIVA, SIN PRODUCTOS INTERMEDIOS
El usuario **NO QUIERE DEMOS, PROTOTIPOS, VISTAS PREVIAS, PANEL SIMULADO NI APK DEBUG como entregables del proyecto**. Quiere trabajar **desde ya en el producto definitivo**, sin reconstruir después lo que se haga ahora. Debes construir una sola solución NEXA V2, formada por **panel web de GESTIÓN REAL y APK Android de GESTIÓN REAL**, sobre **contratos compartidos, datos canónicos y controles auténticos del bot existente**. Básico/Pro son capas de presentación, disponibles en ambas plataformas; NO duplican motores ni lógica.

**Especificación de cierre:** No aceptes como «terminado» el HTML de muestra, \`createDemoProvider()\` como proveedor activo, datos \`fixtures\` en las pantallas reales, PIN \`2468\` hardcoded, acciones que solo muestran «prototipo», endpoints GET no adaptados al contrato, FISCO inaccesible sin solución, un APK sin configuración segura de backend o un enlace público a GitHub Pages para la consola administrativa real. La entrega anterior de \`nexa-v2/\` es una BASE QUE DEBE TRANSFORMARSE, NO el objetivo alcanzado. No generar ni exigir links «DEMO» ni releases «DEMO» como hitos.

**Los tests pueden usar datos sintéticos/fixtures aislados de producción y mocks de API en un entorno de pruebas**; eso es QA interna, no una segunda aplicación ni una entrega intermedia. Mantén una única base de código web+Android y compila el mismo frontend y lógica en ambos.

3. **Conexión a servicios reales como código**: inventariar contratos y rutas actuales del repositorio; adaptadores de lectura y **acciones de gestión** por motor con validaciones, autorización de servidor, estados persistentes, control de errores, idempotencia/reconciliación según semántica original, confirmaciones y auditoría. 4. **Paridad de datos CERO PÉRDIDAS**: las capturas IDCA de Panel/Ciclos/Historial marcan el nivel de detalle mínimo de referencia. 5. **Acceso seguro real**: sustituir PIN fijo DEMO por un sistema seguro, configurable y sin credenciales en cliente/código; sesión con caducidad, permisos por operación, HTTPS, rutas protegidas y logs sin secretos. 6. **Entrega**: web final preparado para alojarse en un entorno administrativo protegido; APK Android compilada, instalada, probada y publicada como asset de descarga en GitHub Releases **solo cuando esté verificablemente preparada**. Incluir hash SHA-256, firma/versión, instrucciones y link directo del asset; no usar rutas locales como entrega. **El enlace al panel web real** debe ser su URL HTTPS protegida una vez el propietario autorice el despliegue; NO suplirlo con un enlace público DEMO. Si no se autoriza aún el despliegue, informar «URL definitiva pendiente de autorización», nunca inventarla.
